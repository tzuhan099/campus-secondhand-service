# 校園二手物精準媒合與保留服務

**Campus Second-hand Match & Hold Service**

> **專案狀態：Design Only（僅規劃，尚未實作）**  
> 本專案為網際服務軟體工程 W02–W07「個人 AI 協作小而美系統規劃與設計」作業。產出 Requirements、RESTful API Design、OpenAPI 3.1.0、Architecture／Data Model 與 AI Collaboration 文件；本次不需程式碼、資料庫或測試。

## 一句話價值主張

透過**商品分類與課程篩選、選填原價的價格對照、可重複公開問答，以及「直接預約或賣家接受交易條件提案即鎖單」**，協助校園使用者更有效率地尋找、了解並保留二手物品，減少重複詢問與多人搶單的混亂。

## 使用者、問題與主要情境

**主要使用者：** 有二手教科書、宿舍家電與日用品買賣需求的大學生、研究生。教職員與學生家長可參與，但本系統**不驗證真實校園身分**。

**要解決的問題：**

1. **難以精準尋找：** 一般社團貼文資訊格式不一，買家不容易按分類、系所或課程找商品。
2. **價格資訊不足：** 缺乏一致的原價與二手售價對照，難以快速比較。
3. **重複詢問與交易條件不易協商：** 商品資訊常分散在私訊，買賣雙方還要逐一討論價格與面交安排。
4. **重複搶單：** 多人同時表達購買意願時，商品實際保留給誰不夠明確。

**具體情境：** 賣家刊登一本教科書，設定售價與校內面交地點，時間可先留空。買家按課程找到商品，公開詢問內容與物況；若接受刊登條件，可直接預約。若希望調整價格、時間或地點，可提出交易條件提案。賣家接受提案時，系統**直接完成預約與商品鎖定**，之後雙方線下面交。

## 系統亮點

### 1. 分類、系所與課程篩選

- 分類限 `TEXTBOOK`（教科書）、`APPLIANCE`（家電）、`DAILY_GOODS`（生活用品）。
- 商品名稱、分類、物況描述及二手售價必填；教科書的「適用系所」與「課程名稱」選填。
- 支援依分類、名稱及教科書的系所／課程關鍵字查詢；預設呈現 `AVAILABLE` 商品。

### 2. 選填原價的價格對照

- **二手售價 `selling_price` 必填且大於 0；購買原價 `original_price` 選填，填寫時須大於 0。**
- 不限制二手售價必須低於原價或原價九折；也**不強制上傳發票、收據或購買憑據**。
- 只有填寫原價時，才計算並顯示 `selling_price / original_price × 100%`（售價占原價百分比）；未填則顯示「原價未提供」。
- 原價由賣家自行提供，**平台不驗證價格真實性**；此資訊只是比較依據，不是鑑價保證。

### 3. 可多次公開提問

- 買家對同一件 `AVAILABLE` 商品可**不限次數**提出公開問題，賣家可逐題回答。
- 所有人可查看問答內容，減少重複詢問；如需追問可另提新問題。
- 商品轉為 `RESERVED` 或 `SOLD` 後，既有問答可查看，但不再新增提問與回答。
- 問答不等於正式提案，不影響兩次提案額度，也不鎖定商品。
- 不提供多層討論、圖片附件、按讚或私人聊天室；不應在公開區張貼個人聯絡資訊。

### 4. 賣家公開交易條件與商品編輯

- 賣家刊登時設定**公開售價（必填）、面交地點（必填）、面交時間（選填）**。地點用文字描述，時間若提供需為未來的明確日期時間。
- `AVAILABLE` 時，賣家可編輯品名、分類、物況、售價、選填原價、教科書資訊，以及面交時間／地點；商品 ID、賣家 ID 不可修改。
- 修改**公開售價、面交時間或地點**時，既有 `PENDING` 提案一律失效（`INVALIDATED`），避免依舊條件成交；已提交的提案次數不重置。
- `RESERVED` 或 `SOLD` 時，不直接編輯原交易條件；預約成立時另保存最後約定條件。

### 5. 每位買家最多兩次正式交易條件提案

- 每位買家對同一商品**最多成功提交兩筆正式提案 `Offer`**；每提交成功一筆即消耗一次，不因拒絕、撤回、失效或取消預約而恢復。
- 提案可修改**價格、面交時間、面交地點**的一項或多項，至少有一個條件不同於目前公開條件；沒有修改的欄位沿用賣家的公開條件。
- 提案價格須大於 0；若議價，須低於當時公開售價，不設定「不得低於五折」的限制。
- 同一買家對同一商品同時間最多一筆 `PENDING` 提案；賣家拒絕第一筆或買家撤回後，買家仍可在剩餘額度內再次提案。
- 提案**僅該買家與商品賣家可查看**，不公開給其他買家；公開問答與正式交易提案分開。
- 提案不設自動到期時間，維持 `PENDING` 直到賣家接受／拒絕、買家撤回，或因商品預約、公開交易條件變更而失效。
- 賣家只需**接受或拒絕**，不提供賣家反向出價或多輪訊息討論。賣家接受提案時，直接完成預約；不要求買家再按一次預約。

### 6. 直接預約與接受提案自動鎖單（核心亮點）

- **方式 A｜直接預約：** 買家接受商品當前公開條件，直接預約 `AVAILABLE` 商品。若賣家未提供面交時間，預約仍可成立，約定時間記為「待線下確認」。
- **方式 B｜接受提案即預約：** 賣家接受某筆 `PENDING` 提案時，系統在**同一原子性交易**內更新提案狀態、建立預約並將商品轉為 `RESERVED`，預約記錄接受後的價格、時間與地點。
- **先成功鎖單者優先：** 若其他買家已直接預約，賣家便不能再接受原本的提案；反之亦然。衝突操作回傳 `409 Conflict`。
- 同一商品同時間最多一筆**有效預約**。鎖單成功後其他 `PENDING` 提案皆改為 `INVALIDATED`，商品不可再被預約或提出新提案。
- 成功預約後，`Reservation` 保存預約買家、約定價格、時間、地點、來源（`DIRECT` 或 `OFFER_ACCEPTED`）。
- **買家本人或賣家**可取消有效預約；商品回到 `AVAILABLE`，舊預約紀錄保留但標記取消，舊提案不會復活，已使用的提案次數不重置。
- 線下面交完成後，**由賣家**確認結案，商品轉為 `SOLD`。不設自動逾期取消或通知排程。

## 核心使用流程（6 步驟）

1. **建立簡化使用者識別：** 使用者設定全站唯一 `nickname`，系統產生 `user_id` 和隨機操作憑證。暱稱衝突回傳 `409 Conflict`；後續操作須驗證憑證，而非只信任暱稱。
2. **賣家刊登商品：** 填寫名稱、分類、物況、售價與面交地點；原價、面交時間、教科書系所／課程為選填。商品初始狀態為 `AVAILABLE`。
3. **買家搜尋與公開問答：** 按分類／課程尋找商品，檢視售價及可用的原價比較，必要時多次公開詢問物況。
4. **選擇交易方式：** 直接接受公開條件預約；或在每商品最多兩次的額度內提交價格／時間／地點的交易條件提案，待賣家接受或拒絕。
5. **立即鎖定：** 直接預約成功，或賣家接受提案時，系統將商品原子性轉為 `RESERVED`，其他衝突操作回傳 `409 Conflict`。
6. **線下面交與結案：** 雙方依最終記錄的條件面交；賣家確認後標記 `SOLD`。若買家或賣家取消預約，商品恢復 `AVAILABLE`。

## 主要業務規則摘要

| 編號 | 規則 |
|---|---|
| BR-01 | `nickname` 全站唯一；操作使用隨機憑證驗證，不以暱稱作為授權憑據。 |
| BR-02 | 商品分類限定三種；教科書的系所、課程選填。 |
| BR-03 | 二手售價必填且大於 0；原價選填，僅用於資訊對照，不驗證憑據、不設折扣上限。 |
| BR-04 | 公開面交地點必填、時間選填；`AVAILABLE` 時可修改商品與交易條件。 |
| BR-05 | 公開問答不限次數，與正式交易提案分開；僅 `AVAILABLE` 商品可新增問答。 |
| BR-06 | 每位買家對同商品最多兩筆成功提交的提案，每次提交計一次；同時最多一筆 `PENDING`。 |
| BR-07 | 提案僅買家與賣家可見；買家可撤回 `PENDING`，賣家可接受或拒絕。 |
| BR-08 | 賣家接受提案時，在同一交易內建立預約、鎖單並保存最後交易條件。 |
| BR-09 | 買家可按公開條件直接預約；不必先提案。 |
| BR-10 | 同商品同時間最多一筆有效預約；先成功鎖單者優先，衝突回傳 `409 Conflict`。 |
| BR-11 | 商品被預約，或賣家修改公開售價／面交時間／地點時，待處理提案失效；次數不恢復。 |
| BR-12 | 買家或賣家可取消有效預約並恢復上架，賣家可確認面交完成；預約歷史保留。 |
| BR-13 | 賣家不得預約或向自己商品提案；不得以其他買家的身分修改商品、提案或預約。 |
| BR-14 | 提案不自動到期；不提供帳號復原、跨裝置登入或身分保證。 |

## 狀態與資料一致性

- **商品 `Item.status`：** `AVAILABLE` → `RESERVED` → `SOLD`；取消預約時 `RESERVED` → `AVAILABLE`。
- **提案 `Offer.status`：** `PENDING` → `ACCEPTED`／`REJECTED`／`WITHDRAWN`／`INVALIDATED`。`ACCEPTED` 必須伴隨成功建立預約，不可出現已接受但未鎖單。
- **預約 `Reservation.status`：** `ACTIVE` → `CANCELLED`／`COMPLETED`。歷史預約留存，同商品只能有一筆 `ACTIVE`。
- **併發控制：** 直接預約和接受提案使用相同的原子性鎖單規則；先成功更新 `AVAILABLE` 者勝出，失敗請求不得產生有效預約。
- **提案使用額度：** 以每位買家對同一商品的已成功提交 `Offer` 筆數計算（包括被拒絕、撤回與失效的提案），不另設可被重置的額度。
- **時間／地點：** 面交地點為文字欄位；面交時間可為空，若為空表示需在線下再確認。系統不提供私人聊天、地圖、行事曆或到場驗證。

## 本次不做什麼（Out of Scope）

- 不處理**線上金流、物流配送或付款驗證**；實際付款與交付在線下進行。
- 不建立完整帳密登入、SSO、JWT、多角色管理或真實校園身分驗證。採簡化隨機操作憑證；**不支援跨裝置登入與憑證遺失復原**。
- 不建立私人聊天室、WebSocket 即時聊天、通知推播或多輪競標；僅有公開問答及結構化交易提案。
- 不強制或提供購買收據上傳、商品照片上傳、外部付費 API、影像辨識、地圖與行事曆整合。
- 不設提案自動到期、預約逾期自動取消、複雜信用評分或評價機制。
- 本次**只做系統規劃與文件設計**，不交付程式碼、資料庫、可執行 API 或自動化測試。

## 預計的主要資料實體

| Entity | 角色與關鍵欄位（初步規劃） |
|---|---|
| `User` | `user_id`（PK）、`nickname`（唯一）、`credential_hash` |
| `Item` | `item_id`（PK）、`seller_id`（FK）、`category`、`selling_price`、`original_price`（可空）、`meeting_time`（可空）、`meeting_place`、`status` |

| `Offer` | `offer_id`（PK）、`item_id`（FK）、`buyer_id`（FK）、`proposed_price`（可空）、`proposed_meeting_time`（可空）、`proposed_meeting_place`（可空）、`status` |
| `Reservation` | `reservation_id`（PK）、`item_id`（FK）、`buyer_id`（FK）、`offer_id`（可空）、`agreed_price`、`agreed_meeting_time`（可空）、`agreed_meeting_place`、`status` |
