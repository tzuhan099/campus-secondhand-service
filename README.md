# 校園二手物交易與預約平台

**Campus Second-hand Trading & Reservation Platform**

> **專案狀態：Design Only（僅規劃，尚未實作）**  
> 本次只交付需求、RESTful API、OpenAPI、架構與資料模型、AI 協作文件，不實作程式、資料庫或測試。

## 一句話價值主張

透過**校園二手商品分類／課程篩選、交易條件提案與一鍵預約鎖單**，讓買家依公開價格、面交時間與地點決定是否預約；賣家接受提案也會立即鎖定商品，避免重複搶單。

## 使用者、問題與使用情境

**主要使用者：** 有二手教科書、宿舍家電或生活用品買賣需求的學生；其他校園相關人士可使用，但本次**不驗證校園身分**。

**要解決的問題：**

1. **尋找商品不便：** 二手社團資訊分散，難以依分類、系所及課程查詢。
2. **交易條件難確認：** 售價、面交日期時間、地點與買家希望調整的條件缺乏統一記錄。
3. **多人重複搶單：** 不容易確認商品是否已保留，可能同時答應多位買家。

**具體情境：** 賣家刊登二手電風扇，填寫售價 500 元、12 月 5 日 15:00 在學校圖書館面交。買家 A 可直接依公開條件預約；也可以提出一次交易條件提案，例如改成 450 元或另一個面交時間。賣家接受提案後，系統自動將商品鎖定給 A；若其他買家先成功預約，該提案就會失效。

## 系統亮點

### 1. 校園導向的商品刊登與篩選

- 商品分類：`TEXTBOOK`（教科書）、`APPLIANCE`（家電）、`DAILY_GOODS`（生活用品）。
- 刊登必填：商品名稱、分類、物況描述、二手售價、**面交日期時間、面交地點**。
- 教科書可選填系所與課程名稱，便於篩選；購買原價 `original_price` 選填，不要求收據或價格證明。
- 可依商品名稱關鍵字、分類、系所、課程與狀態查詢；預設僅顯示 `AVAILABLE` 商品。
- 若有填寫原價，顯示售價占原價百分比；原價為賣家自填，**不代表平台已查證**。

### 2. 交易條件提案：最多兩次

- 每位買家對同一商品最多**成功送出兩筆** `PROPOSAL`，同一時間最多一筆 `PENDING`。
- 買家可調整公開售價、面交日期時間或面交地點的一項或多項；未調整的欄位沿用刊登條件。至少一項須不同；若調整價格，必須大於 0 且低於公開售價。
- 賣家可接受或拒絕 `PENDING` 提案；買家可撤回。每筆提案成功建立即計入兩次額度，**拒絕、撤回或因他人成功預約而失效，都不返還次數**。
- 提案不自動過期，也不提供反向出價；提案內容僅提案買家與商品賣家可查看。
- **有任何 `PENDING` 提案時，賣家不得修改商品的公開售價、面交日期時間或地點**；須先拒絕所有待處理提案或由買家撤回，才能修改。即使原定面交時間已過，仍可拒絕／撤回；違反修改限制回傳 `409 Conflict`，不返還已提交提案次數。

### 3. 直接預約／接受提案即鎖定（核心亮點）

- **直接預約：** 買家接受商品公開的價格、面交時間與地點，送出 `DIRECT` 請求，成功後立即保留商品。
- **提案預約：** 賣家接受 `PROPOSAL` 時，該請求直接轉為 `RESERVED`，商品同步轉為 `RESERVED`，買家不必再次預約。
- **先成功鎖定者優先：** 同一商品同一時間只能有一筆 `RESERVED` 交易請求。其他競爭中的直接預約或提案接受操作回傳 `409 Conflict`。
- 商品鎖定後，其他 `PENDING` 提案轉為 `INVALIDATED`，已消耗的提案次數不返還。
- **有效預約的買家或賣家可取消**，商品恢復 `AVAILABLE`；舊請求及失效提案保留歷史紀錄、不自動恢復。完成線下面交後，由賣家將預約標記為 `COMPLETED`，商品轉為 `SOLD`。
- 賣家不得預約自己的商品；取消後如商品仍可預約，其他買家可建立新請求。

## 核心使用流程（6 步驟）

1. **建立簡化使用者識別：** 使用者建立全站唯一 `nickname`；系統產生 `user_id` 及隨機操作憑證，供後續受保護操作識別身分。
2. **賣家刊登商品：** 設定名稱、分類、物況、售價、**面交日期時間及地點**，商品為 `AVAILABLE`。
3. **買家篩選商品：** 依分類、名稱、系所或課程查看商品與公開交易條件。
4. **選擇交易方式：** 接受公開條件者直接預約；有調整需求者最多提出兩次正式交易提案。
5. **成功鎖單：** 直接預約成功或賣家接受提案時，商品立即轉為 `RESERVED`；其他同時搶單者收到 `409 Conflict`。
6. **線下面交與結案：** 雙方依約定條件自行面交；賣家確認完成轉為 `SOLD`，或由預約買家／賣家取消並恢復商品開放。

## 精簡版 API 與資料實體

本次設計**7 條 RESTful API Operations、3 個主要 Entity**，不另建立問答、聊天室或訂單實體。

| Method | Path | 用途 |
|---|---|---|
| `POST` | `/users` | 建立暱稱與操作憑證 |
| `POST` | `/items` | 刊登商品 |
| `GET` | `/items` | 查詢、篩選商品及公開交易條件 |
| `PATCH` | `/items/{itemId}` | 修改未鎖定商品；有待處理提案時禁止改交易條件 |
| `POST` | `/items/{itemId}/requests` | 建立直接預約或交易提案 |
| `GET` | `/items/{itemId}/requests` | 當事人查詢該商品的交易請求 |
| `PATCH` | `/requests/{requestId}` | 接受／拒絕／撤回提案，取消／完成預約 |

| Entity | 主要用途 |
|---|---|
| `User` | `user_id`、唯一暱稱、隨機憑證雜湊 |
| `Item` | 商品基本資料、公開價格、面交時間地點及商品狀態 |
| `TradeRequest` | 統一記錄 `DIRECT`／`PROPOSAL`、協商條件、成立時交易條件與請求狀態 |

> 主要狀態：商品 `AVAILABLE`／`RESERVED`／`SOLD`；交易請求 `PENDING`／`REJECTED`／`WITHDRAWN`／`INVALIDATED`／`RESERVED`／`CANCELLED`／`COMPLETED`。詳細轉換見需求文件。

## 日期時間與操作識別

- **統一時區：** `Asia/Taipei`（UTC+08:00）；API 日期時間使用 ISO 8601／RFC 3339，範例：`2026-12-05T15:00:00+08:00`。刊登及修改面交時間須為未來時間；`DIRECT` 依公開時間檢查，`PROPOSAL` 依「調整欄位與公開條件合併後」的時間檢查，賣家接受時再檢查提案快照時間。拒絕／撤回提案、取消／完成預約不因約定時間已過而禁止；不做自動到期排程。
- **簡化識別：** 免密碼，不做校園 SSO；註冊時建立不可重複的暱稱及隨機操作憑證，後續用憑證驗證資源操作權限。憑證遺失不可自助恢復，不提供跨裝置登入。
- **面交限制：** 系統提供刊登時公開的交易時間地點，以及經賣家接受後記錄的最終條件；不提供交易成立後改約或站內聯絡方式。雙方自行到指定時間地點面交。

## 本次不做什麼（Out of Scope）

- 不做**公開問答、預約後留言、私人聊天室、即時通知、附件／圖片上傳**或額外聯絡服務。
- 不做線上金流、物流、交易評價、檢舉、信用評分、商品競標、逾期自動取消或排程通知。
- 不做正式會員登入、密碼重設、JWT、SSO、校園身分認證、帳號復原或跨裝置登入。
- 不驗證購買原價、不要求購買證明，也不串接地圖、行事曆、影像辨識或付費 API。
- 不在本次繳交程式碼、資料庫、可執行 API 或測試；僅規劃文件。
