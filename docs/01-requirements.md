# 01｜需求規格（Requirements）

**專案名稱：** 校園二手物交易與預約平台（Campus Second-hand Trading & Reservation Platform）  
**文件狀態：** Design Only（系統規劃，尚未實作）  
**對應文件：** [README.md](../README.md)  

> 本文件以 README 的既定功能與業務規則為基準，說明使用者、情境、功能需求（FR）、業務規則（BR）與驗收標準（AC）。驗收標準描述**未來實作時應可驗證的結果**，不代表本次已完成開發或測試。

## 1. 問題背景與系統目標（Problem & Goal）

校園二手社團的商品資訊常散落在不同貼文，買家不易依商品類別、系所或課程尋找物品；常見的物況問題需要賣家反覆回答；價格、面交時間與地點等交易條件也容易分散在留言中。此外，多名買家表達購買意願時，容易發生重複預約或商品狀態不明確的情形。

本系統聚焦「**查找商品 → 公開問答 → 直接預約／提出交易條件 → 鎖定商品 → 預約後留言 → 線下面交結案**」的主要流程。核心亮點為：**買家直接預約，或由賣家接受提案即自動預約；同一商品在同一時間最多只有一筆有效預約。**

系統僅處理刊登、查詢、協商與預約紀錄，不處理線上付款或物流，也不驗證使用者的真實校園身分。

## 2. 目標使用者與角色（Users）

| 使用者 | 主要行為 | 限制 |
|---|---|---|
| 訪客／一般瀏覽者 | 查詢商品、檢視公開問答 | 不可修改商品、建立提案、預約或查看預約專屬留言 |
| 買家 | 公開提問、提出／撤回提案、直接預約、取消自己的有效預約、於所屬預約留言 | 不可預約自己的商品；不可查看他人的私人提案或預約留言 |
| 賣家 | 刊登／修改自己的商品、回覆公開提問、接受／拒絕提案、取消預約、確認面交完成、於所屬預約留言 | 不可管理他人商品或預約 |

> 買家與賣家是**同一種 `User` 在不同商品交易中的角色**，不建立獨立的管理員與角色權限系統；操作權限依商品及預約的當事人關係判斷。

## 3. 主要使用情境（Scenario）

賣家刊登一台二手電風扇，售價 NT$500，面交地點設為「學校圖書館一樓」，未指定時間。買家 A 篩選家電類商品，公開詢問風扇是否有異音；賣家回答後，其他買家也可查看此問答。

買家 A 希望改為 NT$450、週五下午三點面交，於是提出一筆交易條件提案。若賣家在商品仍為 `AVAILABLE` 時接受該提案，系統**同時**將提案設為 `ACCEPTED`、建立 `ACTIVE` 預約，並將商品改為 `RESERVED`。此後其他買家不能再直接預約；若買家 B 的直接預約先成功，則 A 的待處理提案失效，賣家也不能再接受 A 的提案。雙方可在該筆預約專屬留言區確認面交細節；面交完成後由賣家結案。

如果買家不需要更改條件，也可略過提案，直接依公開售價與地點預約。即使面交時間尚未指定，預約仍可成立，時間顯示「待雙方確認」。

## 4. 功能範圍（Scope）

### 4.1 In Scope

- 全站唯一暱稱與簡化操作憑證識別。
- 二手商品刊登、修改、詳細資訊與條件篩選。
- 賣家自填的選填購買原價及售價比例顯示。
- 商品公開問答（不限提問次數、賣家逐題回覆）。
- 買家提出、撤回交易條件提案；賣家接受或拒絕；每位買家每項商品最多兩次有效提案機會。
- 接受提案自動預約或依公開條件直接預約；競爭請求防重複鎖單。
- 有效預約取消、面交完成、預約後專屬非即時文字留言與歷史查閱。

### 4.2 Out of Scope

- 線上金流、付款證明驗證、物流配送與交易糾紛仲裁。
- 密碼、SSO、JWT、真實校園身分認證、跨裝置登入與帳號復原。
- 購買收據上傳／驗證、商品圖片上傳、地圖及行事曆整合。
- 即時聊天室（WebSocket）、推播、已讀狀態、訊息附件。
- 反向出價、多輪競標、提案自動到期、預約逾時自動取消、評價、檢舉及信用評分。
- 本次不實作程式碼、資料庫或測試；僅完成可供未來實作的設計文件。

### FR-01｜建立使用者與識別操作身分

**需求：** 使用者可建立全站唯一暱稱，系統建立 `user_id` 並核發隨機操作憑證；後續受保護操作必須以有效憑證識別操作者。

**驗收標準（Acceptance Criteria）**

- **AC-01-01：** Given 暱稱尚未被使用，When 提交有效暱稱，Then 建立使用者並回傳 `user_id`、`nickname` 及僅在建立時提供的操作憑證。
- **AC-01-02：** Given 暱稱已存在，When 再次建立相同暱稱，Then 拒絕建立並回傳 `409 Conflict`。
- **AC-01-03：** Given 未提供或提供無效操作憑證，When 嘗試刊登、提案、預約、留言或進行資料變更，Then 拒絕該受保護操作（未驗證回傳 `401 Unauthorized`）。
- **AC-01-04：** Given 使用者 A 的有效憑證，When 嘗試修改使用者 B 的商品或存取 B 與他人之私人交易資料，Then 拒絕操作（已驗證但無權限回傳 `403 Forbidden`，必要時可對隱藏資源使用 `404 Not Found`）。

### FR-02｜刊登與編輯商品

**需求：** 賣家可刊登商品，並於商品尚可預約時編輯自身商品資料和公開交易條件。

**驗收標準**

- **AC-02-01：** Given 賣家已識別身分，When 提交商品名稱、分類、物況、正數售價及非空面交地點，Then 建立商品且狀態為 `AVAILABLE`。
- **AC-02-02：** Given 選填原價或面交時間未填，When 商品其他必填資料有效，Then 可成功刊登；原價及面交時間記為空值。
- **AC-02-03：** Given 分類不屬於 `TEXTBOOK`／`APPLIANCE`／`DAILY_GOODS`、售價非正數、選填原價非正數，或已提供的面交時間不在未來，When 提交刊登，Then 拒絕並回傳欄位錯誤（`422 Unprocessable Content`）。
- **AC-02-04：** Given 商品為 `AVAILABLE` 且操作者為賣家，When 編輯名稱、分類、物況、原價、售價、教科書選填欄位、面交時間或地點，Then 儲存有效變更。
- **AC-02-05：** Given 賣家修改公開售價、面交時間或地點，When 更新成功，Then 原有 `PENDING` 提案皆標記 `INVALIDATED`、原因 `SELLER_TERMS_CHANGED`，且每筆因這次變更失效的提案返還一次提案機會。
- **AC-02-06：** Given 商品為 `RESERVED` 或 `SOLD`，When 嘗試編輯商品，Then 拒絕變更（`409 Conflict`）；`item_id` 與賣家身分不可修改。
- **AC-02-07：** Given 商品為教科書，When 不填系所與課程，Then 仍可成功刊登；若填寫則可供後續篩選。

### FR-03｜查詢商品及價格資訊

**需求：** 使用者可查詢商品列表與詳細資訊，並使用分類、名稱、系所或課程關鍵字篩選。

**驗收標準**

- **AC-03-01：** Given 系統有多筆不同狀態商品，When 未提供篩選條件查詢列表，Then 預設只回傳 `AVAILABLE` 商品。
- **AC-03-02：** Given 輸入分類、名稱關鍵字、系所或課程條件，When 查詢列表，Then 回傳符合條件的商品；沒有符合結果時回傳空列表。
- **AC-03-03：** Given 商品已填寫原價，When 查詢其詳細資訊，Then 顯示售價、賣家自填原價與 `selling_price / original_price × 100%`；未填原價時不計算比例並顯示「原價未提供」。
- **AC-03-04：** Given 查詢商品詳細資訊，When 商品存在，Then 可檢視公開商品資訊及既有公開問答，不得由公開查詢取得私人提案或預約留言。

### FR-04｜公開商品問答

**需求：** 買家可以對可預約商品提出多次公開問題，賣家可針對問題公開回答；所有人均可閱讀。

**驗收標準**

- **AC-04-01：** Given 商品為 `AVAILABLE` 且操作者不是該商品賣家，When 提交非空文字問題，Then 建立公開問題；同一買家可再次建立問題，不設次數上限。
- **AC-04-02：** Given 商品有公開問題且操作者為商品賣家，When 針對指定問題提交回覆，Then 建立指向該問題的公開回答。
- **AC-04-03：** Given 商品為 `RESERVED` 或 `SOLD`，When 嘗試新增公開問題或回答，Then 拒絕新增；既有問答仍可查看。
- **AC-04-04：** Given 已送出公開問題，When 查看買家剩餘提案額度及商品預約狀態，Then 均不受公開提問影響。
- **AC-04-05：** Given 買家或其他非賣家使用者，When 嘗試以賣家身分回答問題，Then 拒絕操作。

### FR-05｜提出與撤回交易條件提案

**需求：** 買家可針對商品公開條件提出有限次數的價格、面交時間或地點調整提案，並撤回尚待處理的提案。

**驗收標準**

- **AC-05-01：** Given 商品為 `AVAILABLE`、買家非賣家、無其他 `PENDING` 提案且尚有次數，When 提交至少一項不同於公開條件的有效調整，Then 建立 `PENDING` 提案並消耗一次額度。
- **AC-05-02：** Given 同一買家對同一商品已有 `PENDING` 提案，When 再次送出提案，Then 回傳 `409 Conflict`，不新增提案且不額外扣次數。
- **AC-05-03：** Given 有效額度已用完，When 再次送出提案，Then 拒絕（`409 Conflict`）；公開提問不納入次數。
- **AC-05-04：** Given 買家提案價格不大於 0、調降價格未低於當時公開售價、提案未改動任何條件，或提出的面交時間不是未來時間，When 提交，Then 拒絕不合法的提案（`422 Unprocessable Content`）。
- **AC-05-05：** Given 買家擁有自己的 `PENDING` 提案，When 主動撤回，Then 提案轉為 `WITHDRAWN`，已使用額度不返還；此後若仍有額度可再提出新提案。
- **AC-05-06：** Given 其他使用者不是提案買家或商品賣家，When 嘗試查看提案詳情，Then 不提供內容；只有當事人可查看。
- **AC-05-07：** Given 商品因賣家更新公開售價、時間或地點使某筆 `PENDING` 提案失效，When 重新計算該買家額度，Then 返還該筆提案消耗的一次；已拒絕或撤回的提案不返還。

### FR-06｜賣家接受或拒絕提案

**需求：** 商品賣家可以接受或拒絕待處理提案；接受時直接建立預約並鎖定商品。

**驗收標準**

- **AC-06-01：** Given 提案為 `PENDING`、商品為 `AVAILABLE`，且操作者為賣家，When 拒絕提案，Then 提案改為 `REJECTED`，商品仍為 `AVAILABLE`，已消耗額度不返還。
- **AC-06-02：** Given 提案為 `PENDING` 且商品為 `AVAILABLE`，When 賣家接受，Then 在同一原子性操作中將提案轉為 `ACCEPTED`、建立一筆 `ACTIVE` 預約、將商品改為 `RESERVED`，並保存接受後的成交價、面交時間及地點；`Reservation.source` 為 `OFFER_ACCEPTED`。
- **AC-06-03：** Given 賣家接受提案鎖定成功，When 檢查同商品其他 `PENDING` 提案，Then 其他提案改為 `INVALIDATED`、原因 `ITEM_RESERVED`，且不返還次數。
- **AC-06-04：** Given 商品已被其他買家成功預約，或提案已不是 `PENDING`，When 賣家嘗試接受該提案，Then 回傳 `409 Conflict`，不得建立第二筆有效預約。
- **AC-06-05：** Given 非賣家使用者，When 嘗試接受或拒絕提案，Then 拒絕操作。

### FR-07｜直接預約

**需求：** 買家不需提案，可直接接受商品目前的公開售價、面交時間（若有）及地點，建立有效預約。

**驗收標準**

- **AC-07-01：** Given 商品為 `AVAILABLE` 且買家不是賣家，When 直接預約，Then 建立 `ACTIVE` 預約、商品改為 `RESERVED`；保存當下公開條件，`Reservation.source` 為 `DIRECT`。
- **AC-07-02：** Given 商品未指定面交時間，When 直接預約成功，Then `agreed_meeting_time` 為空值，畫面顯示「待雙方確認」，不阻止預約成立。
- **AC-07-03：** Given 兩名買家同時直接預約，或直接預約與賣家接受提案同時競爭，When 系統處理請求，Then 最多一筆成功建立 `ACTIVE` 預約，其他衝突請求收到 `409 Conflict`。
- **AC-07-04：** Given 直接預約成功，When 檢查其他 `PENDING` 提案，Then 轉為 `INVALIDATED`（`ITEM_RESERVED`），不返還額度。
- **AC-07-05：** Given 商品已被預約／售出或買家是賣家，When 嘗試直接預約，Then 拒絕操作。

### FR-08｜取消預約與完成交易

**需求：** 預約買家或賣家可以取消有效預約；只有賣家可於線下面交完成後標記交易完成。

**驗收標準**

- **AC-08-01：** Given 預約為 `ACTIVE`，When 預約買家或商品賣家取消，Then 預約轉為 `CANCELLED`，商品恢復 `AVAILABLE`，歷史預約紀錄保留。
- **AC-08-02：** Given 已取消有效預約，When 查詢先前失效的提案，Then 不自動恢復 `PENDING`，也不因取消預約返還提案額度。
- **AC-08-03：** Given 預約為 `ACTIVE` 且面交完成，When 賣家確認完成，Then 預約轉為 `COMPLETED`，商品改為 `SOLD`。
- **AC-08-04：** Given 預約非 `ACTIVE`，或操作者不是該預約的當事人，When 嘗試取消或完成交易，Then 拒絕操作；買家不可自行將預約標記為完成。

### FR-09｜預約專屬留言與紀錄查閱

**需求：** 有效預約雙方可在該筆預約中交換非即時文字留言，用以協調面交細節；預約結束後仍可查看歷史留言。

**驗收標準**

- **AC-09-01：** Given 預約為 `ACTIVE`，When 預約買家或商品賣家提交非空文字留言，Then 留言建立成功，且不限制留言次數。
- **AC-09-02：** Given 其他使用者不屬於該預約雙方，When 嘗試讀取或發送該筆預約留言，Then 拒絕存取。
- **AC-09-03：** Given 預約已為 `CANCELLED` 或 `COMPLETED`，When 當事人查詢留言，Then 可以查看既有內容；若嘗試新增留言則拒絕。
- **AC-09-04：** Given 買賣雙方在留言中約定另一個時間或地點，When 留言送出，Then 不自動更新 `Reservation` 保存的價格、時間、地點或狀態。
- **AC-09-05：** Given 查詢公開問答，When 讀取公開商品資訊，Then 不包含任何 `RESERVATION_MESSAGE` 內容。

## 6. 業務規則（Business Rules）

以下為跨功能共用的正式規則。FR 與驗收標準應遵守相同定義。

| 編號 | 業務規則 |
|---|---|
| **BR-01** | `nickname` 全站唯一，建立使用者時產生 `user_id` 與隨機操作憑證；後續受保護操作依憑證識別，伺服器僅儲存憑證雜湊。 |
| **BR-02** | 商品分類限 `TEXTBOOK`、`APPLIANCE`、`DAILY_GOODS`；教科書的系所與課程選填。 |
| **BR-03** | `selling_price` 必填且 > 0；`original_price` 選填，若提供須 > 0；原價由賣家自填、無需憑據且未經驗證。 |
| **BR-04** | 商品公開面交地點必填且不可為空白；面交時間選填，若填寫於新增／編輯當下須為未來時間。 |
| **BR-05** | `AVAILABLE` 商品接受不限次數的公開提問，只有商品賣家可回覆；`RESERVED`、`SOLD` 僅保留既有公開問答供檢視。 |
| **BR-06** | 每位買家對同一商品同時最多一筆 `PENDING` 提案；有效提案額度上限為 2，每次成功送出即扣 1。 |
| **BR-07** | 提案僅該提案買家及商品賣家可見；買家可撤回 `PENDING`，賣家可接受／拒絕；提案內容一經提交不可編輯。 |
| **BR-08** | 商品仍為 `AVAILABLE` 時，賣家修改公開售價、面交時間或地點，使所有 `PENDING` 提案轉為 `INVALIDATED`（`SELLER_TERMS_CHANGED`），每筆因此失效者返還 1 次額度。 |
| **BR-09** | 賣家接受 `PENDING` 提案時，接受提案、建立 `ACTIVE` 預約及將商品設為 `RESERVED` 必須在同一原子性交易完成。 |
| **BR-10** | 買家可依公開條件直接預約；同商品同時間最多一筆 `ACTIVE` 預約；先成功鎖定者優先，競爭衝突回傳 `409 Conflict`。 |
| **BR-11** | 商品被預約後，其餘 `PENDING` 提案改為 `INVALIDATED`（`ITEM_RESERVED`），不返還提案次數。 |
| **BR-12** | 只有有效預約買賣雙方可新增非即時私人文字留言；預約取消或完成後只能由當事人查閱歷史留言。 |
| **BR-13** | 預約買家或賣家可取消 `ACTIVE` 預約，商品回到 `AVAILABLE`；只有賣家能確認完成，商品轉為 `SOLD`；歷史資料保留。 |
| **BR-14** | 賣家不得向自己的商品提案或預約；商品編輯、提案處理、預約更新及私人資料讀寫只允許相應當事人。 |
| **BR-15** | 提案不設自動到期；不實作帳號復原、跨裝置登入或校園身分認證。 |

### 6.1 提案額度計算與狀態

每位買家針對**單一商品**的剩餘可提案次數為：

```text
remaining_offers = max(0, 2 - submitted_offer_count + seller_terms_invalidated_count)
```

- `submitted_offer_count`：成功建立的所有正式提案筆數（包括 `PENDING`、`ACCEPTED`、`REJECTED`、`WITHDRAWN`、`INVALIDATED`）。
- `seller_terms_invalidated_count`：其中因賣家修改公開交易條件而失效、原因為 `SELLER_TERMS_CHANGED` 的提案筆數。
- 因其他買家預約而失效（`ITEM_RESERVED`）、被拒絕、主動撤回或取消已成立預約，皆**不返還**額度。
- 只有在商品 `AVAILABLE`、沒有自己的其他 `PENDING` 提案且剩餘額度 > 0 時，才能再提出提案。

**例子：** A 第一次提案被拒絕（剩餘 1 次），第二次提案仍為 `PENDING`（剩餘 0 次）；賣家修改公開售價使第二次提案失效，則返還該次機會（剩餘 1 次），第一次拒絕不返還。

### 6.2 提案條件解讀

- 可以調整價格、面交時間或地點中的一項或多項；**未提交的調整欄位**沿用當時商品公開條件。
- 若提出新價格，必須 > 0 且低於當時公開售價（本次僅支援買家要求降價）。
- 若提出新面交時間，必須是提交當下的未來日期時間；若原本未填時間，可透過提案補上時間。
- 若提出新面交地點，必須為非空白文字。
- 至少有一個實際條件與當前公開條件不同；若全部相同，應改採直接預約。
- 提案時間欄位的「未提供」代表**沿用公開時間**，不是要求清除已設定時間；本次不提供買家將已指定公開時間改成「未定」的提案操作。
- 賣家接受提案時，預約記錄完整的有效約定條件（提案調整值與未調整的公開值），不能把未調整欄位誤存為空值。

### 6.3 狀態與轉換

| 資源 | 狀態 | 允許的主要轉換 |
|---|---|---|
| `Item` | `AVAILABLE`、`RESERVED`、`SOLD` | `AVAILABLE → RESERVED`；取消：`RESERVED → AVAILABLE`；完成：`RESERVED → SOLD` |
| `Offer` | `PENDING`、`ACCEPTED`、`REJECTED`、`WITHDRAWN`、`INVALIDATED` | `PENDING →` 其他其中一種終結狀態；`INVALIDATED` 必須記錄原因 |
| `Reservation` | `ACTIVE`、`CANCELLED`、`COMPLETED` | `ACTIVE → CANCELLED` 或 `ACTIVE → COMPLETED` |

**預約一致性：** 直接預約及接受提案共用同一套原子性鎖定規則，避免兩個請求同時看到商品可預約而各自成功。取消預約後僅恢復商品可預約；舊提案不復活、舊預約紀錄保留。

### 6.4 訊息類型與可見性

| 訊息類型 | 關聯對象 | 誰可閱讀 | 誰可建立 |
|---|---|---|---|
| `PUBLIC_QUESTION` | `Item` | 所有人 | 非賣家的已識別使用者，商品為 `AVAILABLE` 時 |
| `PUBLIC_ANSWER` | `Item`＋原問題 | 所有人 | 商品賣家，商品為 `AVAILABLE` 時 |
| `RESERVATION_MESSAGE` | `Reservation` | 該預約買賣雙方 | 該預約買賣雙方，預約為 `ACTIVE` 時 |

公開回答需指向有效的公開問題，不能對其他商品的問題回覆；本次將「逐題回覆」定義為每一題最多一則正式賣家回答，後續若仍需說明可由買家再提出新問題。公開問答與預約留言皆不支援圖片、附件或即時推播。

## 7. 非功能需求與設計約束（Non-functional Constraints）

| 編號 | 規格／限制 | 未來可觀察結果 |
|---|---|---|
| NFR-01 | API 使用 HTTP／JSON，採資源導向的 RESTful 設計 | 後續 API Design 可對應資源、Method、Path 與狀態碼 |
| NFR-02 | 受保護操作應驗證隨機憑證，並依資源當事人判斷存取權限 | 無效憑證不能修改資料，非當事人不能讀取私人提案或預約留言 |
| NFR-03 | 預約鎖定必須具備原子性與一致性 | 同一商品同時最多一筆 `ACTIVE` 預約；競爭請求失敗回傳 `409` |
| NFR-04 | 金額採可精確比較的非浮點表示（如整數新臺幣） | 售價、提案價格與成交價格不因浮點誤差產生錯誤 |
| NFR-05 | 歷史預約與交易留言保留，區分公開與私人資料 | 取消／完成後仍可由當事人查閱，不因商品重新開放而覆蓋舊紀錄 |
| NFR-06 | 本次僅設計，不連接真實第三方服務或敏感個資 | 文件可用模擬使用者、商品及交易資料說明情境 |

## 10. 設計假設與待對齊事項

以下為了讓需求具有可驗收性而明確化的**簡化設計假設**，後續 API、OpenAPI 與資料模型需採同一定義：

1. 買家提出調整面交時間時，必須填寫具體的未來日期時間；省略欄位表示沿用公開設定，不代表要求清空時間。
2. 每個公開問題最多一筆正式賣家回覆；若需追問，買家另外新增一題。這不限制買家總提問次數。
3. 賣家修改「公開售價、面交時間或面交地點」才會使待處理提案失效並返還其額度；僅修改商品描述等欄位不觸發返還。
4. 取消預約後，已成立預約的原始交易條件及留言保留為歷史資料；重新預約會建立另一筆 `Reservation`，不能直接覆蓋舊資料。
5. 預約留言僅用於協調，不自動寫回正式成交價格、時間或地點；本次不提供修改正式預約條件的獨立流程。
