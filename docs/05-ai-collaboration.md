# 05｜AI 協作與設計決策紀錄（AI Collaboration）

**專案名稱：** 校園二手物交易與預約平台  
**專案狀態：** Design Only（僅規劃與設計，未實作程式、資料庫或測試）  

> 本文件依照學生與 AI 的實際討論過程整理重點，不逐字貼出完整對話。表格中的「學生原想法／提問」為對話摘要或意譯；部分構想曾採納、後來又因作業規模調整，不能視為最終功能。最終規格以 `README.md`、`01-requirements.md`、`02-api-design.md`、`03-openapi.yaml` 及 `04-architecture-data-model.md` 為準。

## 1. 協作目的

本次以校園二手交易為題，使用 AI 協助整理需求、討論可行功能、找出流程矛盾、設計 RESTful API，以及檢查跨文件一致性。學生依據實際使用情境和「小而美」作業的建議規模，主動判斷哪些建議適合保留、哪些需要調整或刪除。

**最後聚焦的價值：** 買家可以查看商品的售價、面交時間和地點，選擇直接預約，或有限次數地提出交易條件；只要預約成立，系統就鎖定商品，避免多人重複搶單。

## 2. 四輪主要 AI 協作紀錄

### 第 1 輪｜需求發想與系統功能確認

| 項目 | 討論與決策 |
|---|---|
| **學生原想法／提問** | 希望做一個校園二手物交易服務，讓學生能刊登、尋找教科書或生活用品。初步構想包含全站唯一暱稱、依分類／系所／課程查詢、商品原價與二手售價對照、公開問答、議價，以及預約保留；請 AI 評估是否適合「小而美」系統規範作業。 |
| **AI 建議** | 題目和使用者情境明確，但功能較多；建議先訂出主要亮點，並釐清原價驗證、議價規則及重複預約問題。AI 也提醒：唯一暱稱只能作顯示名稱，不能單獨充當操作驗證。 |
| **自己的判斷與修正** | 決定保留校園二手交易方向，以「預約後立即鎖定商品」作為最重要的亮點。原本曾討論強制填原價、限制二手售價不高於原價九折，以及議價不得低於五折；後來認為原價難以查證、舊商品可能沒有收據，因此改成**二手售價必填、原價選填、不要求購買憑據**，也不採用固定折扣限制。身分識別則採唯一暱稱與簡化隨機憑證，不做完整會員登入。 |
| **階段成果** | 確立使用者、問題與商品資訊欄位；初步決定刊登／篩選／議價／預約的系統方向，以及 Design Only 的作業範圍。 |

**本輪重點：** 並非一開始就確定所有規則，而是先從生活情境確認「有哪些功能真正有用」，再調整不合理的價格限制，逐漸把亮點集中在商品預約與防重複搶單。

### 第 2 輪｜交易流程與使用細節調整

| 項目 | 討論與決策 |
|---|---|
| **學生原想法／提問** | 對最初流程提出進一步修改：同一買家應可多次公開詢問商品；買家也應能調整議價、面交時間與地點；賣家接受提案後，不應還要買家再按一次預約。另外，也考慮預約後如何聯絡對方，以及是否加入留言或私聊。 |
| **AI 建議** | 將公開問答和正式交易提案區分；正式提案可由賣家接受／拒絕，接受後即預約鎖單。若缺乏聯絡管道，可以考慮簡化的非即時留言，不必使用 WebSocket 聊天室；但需考慮訊息權限、預約後協調和 API 數量。 |
| **自己的判斷與修正** | 階段性採納**公開問答可重複提問**、**買家對同一商品最多兩次正式提案**、**提案可調整價格／時間／地點**、**賣家接受即自動預約**等規則。也曾決定加入「預約成立後的專屬留言區」，解決面交時間未確定時無法聯絡的問題。交易提案僅買賣雙方可查看，不當作公開競標；商品預約採先成功鎖定者優先。 |
| **階段成果** | 需求從單純商品刊登擴充到公開問答、條件協商、預約鎖定和交易後留言，流程更加完整，但功能範圍也因此擴大。 |

**本輪重點：** 學生不是直接接受 AI 生成的功能表，而是從「買家會問什麼？如何議價？接受提案後是否還要預約？約好之後怎麼聯絡？」等實際情境補充細節。這些功能在本輪是**階段性方案**，不代表最後都保留。

### 第 3 輪｜API 過多後主動收斂範圍

| 項目 | 討論與決策 |
|---|---|
| **學生原想法／提問** | 完成初版需求與 API 設計後，發現規劃達 **18 條 API、5 個主要 Entity**，比老師建議的 2–4 條必要 API Operations、1–3 個主要 Entities 多很多，因此主動詢問能否精簡至最多 6～7 條 API；即使刪減部分功能也可以，優先符合本次系統的主要目標。 |
| **AI 建議** | 將原本分開的 `Offer`（議價提案）與 `Reservation`（預約）整合成 `TradeRequest`；保留「商品刊登／查詢、直接預約、提出交易條件、賣家接受後鎖單、取消／結案」，移除需要較多 API 和存取控制的公開問答、預約後留言。 |
| **自己的判斷與修正** | **接受精簡方向，但保留交易條件提案和預約防撞單這兩項核心設計。** 認為只要刊登時已提供明確的售價、面交日期時間與地點，有興趣的買家就能判斷要直接預約或提出不同條件，因此決定取消公開問答、預約後留言與私人聊天，並將面交日期時間和地點改為刊登必填。 |
| **階段成果** | 從 **18 條 API、5 個 Entity** 收斂為 **7 條 API、3 個 Entity（`User`、`Item`、`TradeRequest`）**；需求同步整理為 6 項 FR、12 項 BR，保留單一主要交易流程。 |

**這輪是「不完全採納 AI 建議」及學生主動取捨的代表：** 先前曾依 AI 建議加入交易後留言，後來學生發現 API 規模過大，明確要求縮減，並決定暫時不做訊息功能。這個選擇犧牲了預約後的站內溝通與改約能力，但讓整份作業更能呈現主要問題、必要 API 與一致的資料模型。

**精簡後的業務規則：**

- 商品刊登時須提供二手售價、面交時間及面交地點；原價選填。
- 買家可以直接預約（`DIRECT`），或最多提出兩次正式交易條件提案（`PROPOSAL`）。
- 賣家接受 `PENDING` 提案，即同步鎖定商品；先成功預約者優先。
- 若商品已有待處理提案，賣家不得修改公開售價、面交時間或地點，以免增加提案失效後返還次數的規則；相關衝突回傳 `409 Conflict`。
- 取消預約可重新開放商品，完成面交則標記售出；此次不加留言、通知、金流或物流功能。

**精簡後的 7 條 API：**

| API | Method | Path | 用途 |
|---|---|---|---|
| API-01 | `POST` | `/users` | 建立使用者 |
| API-02 | `POST` | `/items` | 刊登商品 |
| API-03 | `GET` | `/items` | 查詢及篩選商品 |
| API-04 | `PATCH` | `/items/{itemId}` | 編輯商品 |
| API-05 | `POST` | `/items/{itemId}/requests` | 直接預約／交易提案 |
| API-06 | `GET` | `/items/{itemId}/requests` | 查詢交易請求 |
| API-07 | `PATCH` | `/requests/{requestId}` | 接受、拒絕、撤回、取消或完成交易 |

老師的 2–4 條 API 為**建議規模而非硬性上限**；本次選擇 7 條，是為了保留一條可以完整完成「刊登 → 查詢 → 預約／提案 → 結案」的流程，而非為了達到固定數字犧牲必要的查詢與狀態更新操作。

### 第 4 輪｜文件撰寫與跨文件一致性檢查

| 項目 | 討論與決策 |
|---|---|
| **學生原想法／提問** | 要求 AI 同步重寫 `README.md`、`01-requirements.md`、`02-api-design.md`，避免仍殘留已刪功能；再逐項檢查 API 是否寫明 Resource、Method、Path、用途、成功／失敗狀態碼及對應 FR。其後依新版 API 編寫 `03-openapi.yaml`、`04-architecture-data-model.md`，並使用 Swagger Editor 查看 Schema 顯示情況。 |
| **AI 建議／檢查重點** | 檢查 FR、業務規則、7 條 API、Schema 名稱、狀態轉換及 Entity 關聯；核心預約不可只靠「查詢後更新」，需規劃原子性鎖單；OpenAPI 要包含參數、必填欄位、回應、錯誤格式、型別與 `$ref`。 |
| **自己的判斷與修正** | 採用 7 條 API／3 個 Entity 版本作為後續文件唯一基準；確認 API 採資源導向命名、使用 `POST`／`GET`／`PATCH` 表達操作，日期時間以臺北時間 `Asia/Taipei`（UTC+08:00）為準。依老師規範要求在文件呈現 Router → Service → Repository、Request Flow、PK／FK、Relationships 與需求追溯。 |
| **階段成果** | 完成 OpenAPI 3.1.0 契約與架構／資料模型初稿。 |

**跨文件追溯例子：**

`FR-04 建立交易請求 → API-05 POST /items/{itemId}/requests → TradeRequestCreateRequest／TradeRequestResponse → TradeRequestsRouter → TradeRequestService → ItemRepository／TradeRequestRepository → Item／TradeRequest`

**核對重點：**

| 項目 | 最終約定 |
|---|---|
| 功能需求 | FR-01～FR-06，共 6 項 |
| API | API-01～API-07，共 7 條，路徑均使用名詞資源 |
| 主要 Entity | `User`、`Item`、`TradeRequest`；以 PK／FK 表示關聯 |
| 鎖單規則 | `DIRECT` 立即保留；`PROPOSAL` 被接受後保留；同一商品最多一筆有效預約 |
| 衝突處理 | 非法狀態轉換、重複預約或受限的交易條件修改等情境使用 `409 Conflict` |
| 時間格式 | `Asia/Taipei`，對外使用含 `+08:00` 時區偏移的日期時間 |

> Swagger Editor 能用於檢查 OpenAPI 契約，但 Schema 正常呈現不代表服務已實作或完成 API 測試；本作業維持 Design Only。

## 3. 最終範圍與設計取捨

| 最終保留（In Scope） | 本次不做（Out of Scope） |
|---|---|
| 商品刊登、編輯、分類／系所／課程篩選 | 公開問答、私人聊天室、預約後留言 |
| 售價必填、原價選填、面交時間與地點必填 | 原價憑據驗證、圖片與附件上傳 |
| 最多兩次提案、直接預約與接受提案後鎖單 | 無限制協商、競標、通知與自動排程 |
| 取消預約、完成交易與歷史請求紀錄 | 金流、物流、評價及完整會員登入／帳號復原 |

**取捨理由：** 完整的溝通功能雖然能增加便利性，但也會帶來更多訊息資料、存取權限、API 與業務規則。這次以「先把價格、時間、地點說清楚，讓使用者完成預約保留」作為最小範圍，將聊天室、公開留言等留待未來再評估。
